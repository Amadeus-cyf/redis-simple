# Measurement scripts

Scripts that measure the whole server. Run them from the repository root.
None of them is part of CTest or CI.

Two scripts measure the whole server under load generated by
`redis-benchmark`. Each takes a server binary and, optionally, a baseline
binary to compare against:

```sh
# Instructions executed per workload, with callgrind (Linux, needs valgrind)
scripts/measure/profile_server.sh build/release/redis_simple path/to/baseline/redis_simple
# Resident memory per key after loading 3-, 36-, and 100-byte values
scripts/measure/measure_server_memory.sh build/release/redis_simple path/to/baseline/redis_simple
```

`profile_server.sh` runs eleven workloads: a small command mix, pipelined and
unpipelined `GET`/`SET`, 4 KB and 36-byte values, 1,000-member collection
reads, writes with AOF on, keys with TTLs plus `SCAN`, saving and loading
an RDB file of every type, replaying an AOF, and editing lists by
position. Pick some with
`-w`, for example `-w unpipelined,aof-writes`. It counts instructions rather
than time because counts barely vary between runs, so differences of a few
percent are reliable even on a busy or small machine. Counts miss cache-miss
costs, so confirm large changes with `redis-benchmark` throughput on a quiet
machine. Set `PROFILE_OUTPUT_DIR` to keep the callgrind files, which
`callgrind_annotate` breaks down by function.

`scripts/measure/compare_callgrind.py BASELINE.cg BINARY.cg` lists the functions
whose instruction counts changed most between two such files, which shows
where a regression comes from.

`measure_server_memory.sh` reports idle and loaded RSS and bytes per key.
Its keys are 16 bytes long; a key's entry is 56 bytes plus its name (64 plus
its name with libstdc++), rounded up to the allocator's size class, and the
same with or without a TTL.
`MEMORY_VALUE_SIZES`, `MEMORY_REQUESTS`, and `MEMORY_KEY_RANGE` change the
load.

Instruction counts and memory per key miss work outside the request path,
so three more scripts cover it. Each takes any number of binaries,
`redis-server` included, and runs each in a fresh server:

```sh
# Pauses other clients see during DEL, UNLINK, FLUSHDB, BGSAVE, and
# BGREWRITEAOF, and how long after the last deadline expired keys are gone
scripts/measure/measure_pauses.py build/release/redis_simple path/to/baseline/redis_simple redis-server
# System calls per connection and per request (Linux, needs strace)
scripts/measure/count_syscalls.py build/release/redis_simple path/to/baseline/redis_simple redis-server
# How a BGSAVE or rewrite writes its file: dirty pages (Linux), page cache
# left behind, and, with --trace (Linux, needs strace), the sync calls
scripts/measure/measure_snapshot_io.py build/release/redis_simple path/to/baseline/redis_simple redis-server --trace
```

`measure_pauses.py` times with a PING loop, so its numbers vary between
runs; compare large effects, such as a pause of tens of milliseconds, and
repeat a run before reporting a small one. Its `window s` column is how
long the PING columns cover; compare `>1ms` counts only between rows with
similar windows. `-s` picks scenarios and `-n` the number of keys or
elements. `count_syscalls.py` attaches strace after startup, so the counts
cover only the workload; `connect` opens a connection per request, which no
other script does. strace slows the server, so compare binaries rather than
reading the counts as absolute. `measure_snapshot_io.py` must write to a
disk, not a tmpfs; pass `--dir` if the temporary directory is one.

Two more scripts time the server itself, and run on macOS as well as
Linux:

```sh
# Markdown tables for a pull request: requests per second, p50 and p99
# latency, and server CPU for ten workloads, then memory for strings,
# collections, and idle connections
scripts/measure/compare_builds.py path/to/baseline/redis_simple build/release/redis_simple
# Server CPU seconds for one redis-benchmark workload of your choice
scripts/measure/measure_server_cpu.sh 7460 7 build/release/redis_simple path/to/baseline/redis_simple -- -t set,get -n 2000000 -P 16
```

Both start a fresh server per measurement and alternate between the two
builds. `compare_builds.py` reports the median of `--runs` runs for
throughput and latency and the minimum for CPU; `--only latency` or
`--only memory` prints one table, and `--case TEXT` only the rows whose
label contains the text. Throughput and latency vary by a few percent
between runs, so trust the CPU column for small differences, and prefer
instruction counts where callgrind runs. Its memory is resident memory on
Linux and the physical footprint on macOS, where resident memory keeps
counting pages the allocator has returned. `measure_server_cpu.sh` takes
extra server arguments in `SERVER_ARGS`, and data to load first in
`PRELOAD` (`redis-benchmark` arguments) or `PRELOAD_CLI` (a `redis-cli`
command).

These scripts need `redis-benchmark` and `redis-cli`, which ship with
Redis (`brew install redis` or `apt install redis-tools`). Like the
benchmarks, they are not part of CTest or CI.
